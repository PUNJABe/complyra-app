# Deployment and operator setup

This repository is an implementation ready for configuration and testing. No PostgreSQL/Oracle database, Resend account, AI credentials, DNS, cloud network or scheduler was supplied or provisioned. Do not put real financial records into development mode. The existing `.complyra/mock-db.json` is not imported or served by the new private workspaces.

## [GitHub Pages](https://docs.github.com/en/pages) frontend with [GitHub Actions](https://github.com/features/actions)

GitHub Pages hosts the static frontend only. Keep the existing Next.js API routes on a separate HTTPS Node.js host with PostgreSQL/Oracle, Resend/SMTP, and any AI secrets; Pages cannot execute these APIs or scheduled reminders. The `Deploy static frontend to GitHub Pages` workflow exports the existing UI and publishes it when `main` is updated. Set repository variable `NEXT_PUBLIC_API_BASE_URL` to the backend origin, such as `https://api.example.com` (origin only, no path). In the backend environment, set `APP_ORIGIN` to the exact browser origin and `APP_URL` to the full frontend URL, including the repository path for a project Pages site.

For session cookies to work reliably, use a custom frontend domain and host the API on a subdomain of that same domain (for example, `app.example.com` and `api.example.com`). The browser sends the HttpOnly `SameSite=Lax` session cookie to the API with credentialed CORS requests; unrelated `github.io` and backend domains are cross-site and browsers may block their cookies. The backend proxy permits CORS only from `APP_ORIGIN` and still validates mutation origins.

In the repository settings, enable Pages with **GitHub Actions** as the build and deployment source. The workflow currently deploys from `main`; change its branch trigger if the default branch differs. The export path is computed for project Pages and user/organization Pages automatically.

GitHub Pages cannot configure the application's CSP and other response security headers. The static frontend therefore does not receive the per-request CSP or custom headers configured for the server-hosted app. Dashboard/admin page shells are public static HTML; private data and changes remain behind the backend API's session and role checks. Review these hosting limitations before using it with real financial data.

## [Render](https://render.com/) API, [Neon PostgreSQL](https://neon.tech/) and [Resend](https://resend.com/) email

1. Create a Neon project and database, copy its pooled PostgreSQL connection string, then run [db/postgres.sql](../db/postgres.sql) once. Store the connection string as the Render `DATABASE_URL` secret; never commit it. The app encrypts stored records before writing them to PostgreSQL, so also configure a generated `DATA_ENCRYPTION_KEY` containing **64 hex characters**. Generate it with `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"` and keep it outside the repository. Losing this key loses access to encrypted records.
2. Deploy this repository to Render using the included [render.yaml](../render.yaml) Blueprint. Set `DATABASE_URL`, `DATA_ENCRYPTION_KEY`, `APP_ORIGIN`, `APP_URL`, `RESEND_API_KEY` and `MAIL_FROM` in the Render dashboard. `APP_ORIGIN` is the frontend origin only (scheme and hostname); `APP_URL` is the complete frontend URL and may include the GitHub Pages project path.
3. In Resend, verify `complyra.site` and set `MAIL_FROM` to `Complyra <no-reply@complyra.site>`. Use `complyra.co@gmail.com` for the Resend account/contact and as a recipient for test mail if desired; Resend cannot send as a public Gmail address because Gmail's domain is not yours to verify. The API key is used only by the server to send verification and reset emails.
4. Configure the GitHub repository variable `NEXT_PUBLIC_API_BASE_URL` to the Render API origin, and enable GitHub Pages with **GitHub Actions** as the source. The workflow publishes `complyra.site` as the custom domain and derives the correct base path. Push to `main` to build and publish the static frontend.
5. To use login reliably, use `complyra.site` for the frontend and `api.complyra.site` for the API. Point the frontend domain at GitHub Pages and add `api.complyra.site` as a custom domain in Render, then create the DNS record Render specifies. Set Render `APP_ORIGIN` to `https://complyra.site` and `APP_URL` to the same URL. These hosts share a registrable domain, allowing the credentialed API session cookie to work as same-site while keeping separate origins. DNS can be managed at Namecheap; Cloudflare DNS is another free service for a domain you already own.

The included Render Blueprint selects its free web-service plan, which may sleep when idle and is intended for evaluation rather than dependable production use. Neon and Resend free-plan quotas and terms can change; confirm current limits in each provider's dashboard. GitHub Pages cannot set the server-side CSP/security headers used by the full Next.js deployment. Do not treat the free-tier combination as a production security or availability guarantee.

The app's authentication, password hashing and session lifecycle are implemented in [src/lib/auth.ts](../src/lib/auth.ts). Email delivery is implemented in [src/lib/mail.ts](../src/lib/mail.ts), which uses Resend when `RESEND_API_KEY` is configured and retains the SMTP/outbox development paths. These files are named differently from `auth.service.ts`, `email.service.ts` and `session.ts` in the requested architecture.

The Neon/PostgreSQL adapter is selected with `COMPLYRA_STORAGE_MODE=postgres`. It stores the app's encrypted key-value records, including accounts, authentication state and workspaces, in `complyra_kv`. It does not create normalized per-account tables. No automatic migration from an existing Oracle or local-file deployment is included; plan and validate a data migration before changing the storage mode for any deployment containing user data.

## Oracle Autonomous Database (alternative)

1. In your Oracle tenancy, create an eligible Always Free Autonomous Database in your chosen Indian region when available. Check current service eligibility and capacity in your own console; no resources are provisioned by this repository.
2. Create a dedicated application schema with only session access, quota and ownership of its application table. Do not give the web process the Oracle `ADMIN` credentials. Run [db/oracle.sql](../db/oracle.sql) once as that schema owner.
3. Download the mTLS wallet from the database connection console. Store it outside the repository with restricted access. Configure `ORACLE_WALLET_LOCATION`, `ORACLE_WALLET_PASSWORD`, the TNS service alias in `ORACLE_CONNECT_STRING`, `ORACLE_USER` and `ORACLE_PASSWORD`. Alternatively use the database's full TCPS descriptor with server certificate verification and its approved access restrictions. The driver runs in Thin mode; Oracle Instant Client is not required for this path.
4. Set `COMPLYRA_STORAGE_MODE=oracle`, `APP_ORIGIN` to the exact frontend origin, `APP_URL` to the full frontend URL, and a generated `DATA_ENCRYPTION_KEY` containing **64 hex characters**. Generate it with `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`. Keep it in a secret manager. Losing this key loses access to encrypted records. Changing it requires a deliberate migration; there is no automatic key rotation.
5. Only the application tier should reach the database. Use private endpoints and VCN routing where supported, or tightly restricted database access controls for your application egress. Enable TLS at the public ingress and enforce a 6 MB request-body limit and an appropriate request timeout. Do not expose the Node origin directly. Configure a WAF/rate limiter at ingress. If using `TRUSTED_CLIENT_IP_HEADER`, ensure ingress **removes and overwrites** the client-supplied value; otherwise leave it blank (a shared auth ingress limit applies).
6. Start the application and exercise registration, verification, import, review and export against Oracle in staging. Test two application instances concurrently. The KV adapter uses bind variables, CLOBs, transactions and `SELECT ... FOR UPDATE` to serialize mutations; workspace revision checks reject stale replacements rather than silently overwriting another change. Oracle errors never fall back to local files.

Production refuses local-file storage and missing encryption keys. Local mode uses atomic file replacement and in-process serialization and is **only for a single development process**. This first database integration stores encrypted documents by account key, rather than pretending to be a normalized accounting ledger. The global security document serializes account/session changes and should be split into indexed account/session tables before high-volume deployment. The current product is limited to 2,000 active statement records per account.

Oracle reference: [node-oracledb Autonomous Database connections](https://node-oracledb.readthedocs.io/en/latest/user_guide/connection_handling.html#connecting-to-oracle-autonomous-database-adb).

## Email, administrators and scheduling

- Configure a verified sender and `MAIL_FROM`; Resend API delivery via `RESEND_API_KEY` is preferred, while SMTP on port 465 (implicit TLS) or 587 (STARTTLS) remains supported. Configure your sender domain's SPF, DKIM and DMARC with the provider. Verification/reset links use the configured origin, never an incoming Host header. Tokens expire in 30 minutes and are stored as hashes. No account or session is created by requesting a registration email. The verification page confirms by POST to avoid link scanner/prefetch activation.
- Set `ADMIN_EMAILS` **before** the intended administrator registers and verifies. Public request bodies cannot assign roles. New accounts otherwise receive `employee`; admin changes can assign `viewer`, `employee`, `ca` or `admin`. Roles govern access, not workspace sharing: every account currently has a private workspace. There is no shared team workspace or delegated accountant access yet. A viewer can read/export workspace records and manage its own account, password, privacy choices and deletion, but cannot modify financial records.
- Configure `AUTH_BLOCKLIST`, `AUTH_ALLOWLIST`, and `AUTH_ALLOWLIST_ONLY` as needed. Exact email and `@domain` entries are supported. Blocklist takes priority. The admin panel maintains additional rules, disables users and revokes affected sessions. Admin self-lockout through panel changes is rejected. Server environment rules are operator-controlled.
- Generate a separate random `CRON_SECRET` of at least 32 characters. Schedule an authenticated `POST /api/cron/reminders` every hour with `Authorization: Bearer <secret>`. Never place this secret in client code or a public URL. In-app reminders calculate 24 hours from registration or the last successful import. Email reminders are opt-in; delivery is limited to once per 24 hours per account, with a five-minute claim lease and retry on failure. SMTP cannot guarantee exactly-once delivery across a crash after sending. Monitor failures and the scheduler externally. No browser must be open for scheduled email delivery.
- Optional: set `OPENAI_API_KEY` and `OPENAI_MODEL`. AI is off per account until explicit opt-in. Categories with unclear evidence remain in the human review queue. The configured model is not trained on corrections by this app; explicit remembered merchant rules are local to the account. Review processor terms, region, retention and redaction before enabling AI for real records. External AI calls are limited to 30 per account per hour, with local assistance used when this allowance is reached.

## India launch requirements

The user confirmed India and has not yet chosen a business identity/contact. The supplied privacy, terms, cookies and acceptable-use pages are **drafts**. Production registration stays closed until `LEGAL_ENTITY_NAME`, `PRIVACY_CONTACT_EMAIL` and `LEGAL_POLICIES_APPROVED=true` are set. This flag is an operator attestation, not automated certification.

Before setting the flag, review actual processing and launch terms with an appropriately qualified adviser: identify the operator/grievance contact, lawful processing grounds, age/authority handling, processors and cross-border arrangements, backup/log retention, data subject request process, incident response and statutory obligations. Assess the phased DPDP Act/Rules effective dates against the actual launch date and business. This software does not certify universal compliance or validate GST/invoices from bank narrations. Publish additional information and request renewed consent when processing materially changes. No paid billing terms or regulated advisory service are implemented.

Official source: [MeitY DPDP Rules 2025](https://www.meity.gov.in/documents/act-and-policies/digital-personal-data-protection-rules-2025-gDOxUjMtQWa).

## DMZ and decoy deployment

The `security/decoy` service returns only synthetic records and imports no application modules. Its optional Compose file runs it read-only, without production environment variables or mounted volumes, on an internal network bound to loopback port 8089. Build it separately with `docker compose -f security/decoy/compose.yaml up --build -d` on an appropriately isolated host. Docker was not assumed installed or run by this implementation.

For an actual cloud DMZ, deploy this service in a separate subnet/network or host with **no routes or credentials to the application/database networks**, deny outbound traffic, and forward selected decoy-only paths from a public edge to it. Forward only security telemetry to an independent monitoring destination; monitor decoy hits and never promote synthetic records into user reports. Keep the real app, wallet and encryption key on the private application tier. Do not automatically reroute legitimate API calls based on an unvalidated attack classifier. A decoy can detect reconnaissance and expose fake records on its own endpoints; it does not prevent a successful attacker reaching a vulnerable real endpoint. Network deployment and penetration testing remain operator work.

## Validation and operations

- Run `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`, and `npm audit --omit=dev`.
- The automated integration test starts an isolated local server and temporary data directory; it tests verification, forged cookies, API guards, cross-account isolation, remarks, block/allow rules, recovery, revocation, and reminder delivery through a local outbox. It does **not** validate a real Oracle tenancy, SMTP delivery or model account. Use staging credentials for those smoke tests.
- Keep originals and encrypted backups. Define retention and perform a restore rehearsal. Account deletion empties the live workspace with a deletion marker, removes account/tokens, revokes sessions, and anonymizes its security-event identity; the operator must handle provider logs and backups under its published retention obligations. Data is not physically scrubbed from backups by the app.
- Password hashing follows [OWASP scrypt guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) (`N=2^17`, `r=8`, `p=1`, random salt). Sessions are opaque random tokens with hashed server-side verifiers, 30-minute inactivity expiry and a seven-day absolute limit. There is no MFA enrollment or claim of MFA support in this release.
- Apply dependency updates and independent security review before real-data deployment. Current cookies and CSP do not replace ingress controls, patching, monitoring or incident response.
